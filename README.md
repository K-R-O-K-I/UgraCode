# Ясна — запись и учёт занятий

Веб-приложение для детской столярной мастерской «Ясна» в Сургуте.
Мастер управляет расписанием, посещениями и расчётами. Родитель записывает
детей, видит остатки абонементов, оплачивает занятия и получает чеки.

## Текущее состояние

Подготовлены описание решения и проект физической схемы БД.
Приложение, Django-модели, миграции и окружение запуска ещё предстоит создать.
Этот README описывает план работы, а не уже реализованные возможности.

- [Архитектура и правила работы с данными](Архитектура/README.md)
- [Проект схемы PostgreSQL](Архитектура/schema.sql)
- Репозиторий: https://github.com/K-R-O-K-I/UgraCode

SQL — материал для реализации Django-моделей. Не запускайте его поверх базы,
созданной миграциями Django: это два разных способа создания таблиц.

## Что делаем первым

Первая контрольная точка — одинаково запускающийся каркас на всех трёх ноутбуках.
Вторая — один работающий сценарий от записи до остатка абонемента.
Не начинаем с полной CRM, красивого лендинга или трёх независимых приложений.

### Распределение на старте

Номера ниже обозначают роли. Перед работой закрепите их за конкретными людьми
в GitHub Issues. Предлагается, чтобы инициатор проекта взял роль 1.

| Роль | Ответственность | Первая задача | Как понять, что готово |
| --- | --- | --- | --- |
| 1. Основа и интеграция | Каркас, окружение, accounts/core, согласование моделей, сборка | Создать Django-проект, подключить PostgreSQL, подготовить общие модели и запуск | Все трое запускают проект по README; работают миграции и вход в admin |
| 2. Расписание и мастер | scheduling, запись, отмены, журнал, страницы мастера | После основы сделать список занятий и запись ребёнка | Можно записать ребёнка; повторная запись и превышение вместимости запрещены |
| 3. Абонементы и родитель | billing/notifications, кабинет, платежи и чеки | После основы сделать ручную оплату и выдачу абонемента | Оплата выдаёт четыре занятия ровно один раз; остаток виден в кабинете |

Пока роль 1 готовит каркас, роль 2 описывает поля и сценарии расписания,
роль 3 — расчётов и кабинета. Можно нарисовать экраны, составить проверки и Issues.
Не создавать отдельные Django-проекты. Общие модели и названия согласовать вместе.

У роли 3 большая нагрузка: после первого рабочего сценария роль 1 помогает
с ЮKassa и проверками, роль 2 — с интерфейсом родителя.

## Стек и структура

Python, Django 5.2 LTS с актуальными исправлениями, PostgreSQL,
Django Templates, Bootstrap. HTML формируется сервером, действия отправляются
обычными формами. Отдельный frontend и собственный JavaScript на старте не нужны.
Точные версии Python, PostgreSQL и зависимостей фиксирует роль 1 при сборке основы.

Планируемая структура (эти каталоги приложения пока не созданы):

```text
manage.py
config/          # настройки, корневые URL
accounts/        # семьи, дети, ссылки доступа
scheduling/      # занятия, записи, посещаемость
billing/         # тарифы, счета, платежи, абонементы, чеки
notifications/   # сообщения в кабинете
core/            # аудит, экспорт, демоданные
templates/       # страницы и общий base.html
static/          # оформление
Архитектура/     # решения и схема БД
```

Django Admin нужен для первоначального ввода и настройки данных.
Мастер и родитель получают отдельные страницы для ежедневных действий.
Бизнес-операции располагаем в services.py соответствующего приложения;
views.py принимает запрос и вызывает сервис, шаблоны отображают результат.

## Первый сквозной MVP и результат для заказчика

Первый внутренний MVP: семья с двумя детьми → запись на занятие → ручная
оплата абонемента на четыре занятия → отметка посещения → остаток три
в кабинете родителя. Это контрольная точка разработки, а не полное выполнение кейса.

Для результата по заданию также обязательны тестовая онлайн-оплата, чеки,
уведомления, настраиваемые правила, защита доступа, выгрузка и резервирование.

Сценарий демонстрации:

1. Создать группу на два места и семью с двумя детьми.
2. Записать ребёнка.
3. Оплатить абонемент на четыре занятия тестовым платежом.
4. Отметить посещение и показать остаток три.
5. Прикрепить чек и открыть его из родительского кабинета.
6. Заполнить группу и показать отказ следующему желающему.
7. Повторить уведомление об оплате и показать, что начисление не повторилось.

Лист ожидания, мессенджеры, импорт из «МойКласс», полноценный сайт и глубокая
интеграция с ВК — после обязательного сценария. Чек формирует мастер в «Мой налог»;
наше приложение хранит файл или ссылку, не формирует чек автоматически.

## Правила данных, которые нельзя менять независимо

- Семья объединяет детей. Доступ родителя всегда ограничен своей семьёй.
- Вместимость проверяется сервером в транзакции с блокировкой занятия.
- Деньги и оставшиеся занятия учитываются отдельно.
- Списание сохраняется отдельной операцией. Исправление создаёт обратную запись.
- Повторное действие или уведомление платежа не должно повторять начисление.
- Чеки доступны после проверки прав; секреты и данные семьи не передаются в публичный репозиторий.
- Правила отмен настраиваются, история изменений сохраняется.

Предложения, ещё не подтверждённые заказчиком: мастер создаёт семью и передаёт
ссылку; абонемент принадлежит одному ребёнку; срок начинается с полной оплаты.
При изменении этих условий сначала обновляем архитектуру и модели вместе.

## Как работать через GitHub

1. Владелец добавляет двух участников в Collaborators. Каждый клонирует
   https://github.com/K-R-O-K-I/UgraCode на свой ноутбук.
2. Перед задачей обновить main и создать отдельную ветку, например feat/booking.
3. Указать себя исполнителем Issue. Зафиксировать ожидаемый результат и файлы,
   которые собираетесь менять, особенно общие настройки и модели.
4. Делать небольшие завершённые изменения, проверять, сохранять commit и push.
5. Открыть Pull Request: что изменилось, как проверить, есть ли миграции.
6. Другой участник проверяет сценарий и код. Затем объединить в main и удалить ветку.
7. Остальные обновляют main, устанавливают изменённые зависимости и применяют миграции.

main должен запускаться. Не создаём постоянные ветки по людям и не откладываем
объединение частей на конец хакатона. Не используем force push в общую main.
GitHub Desktop подходит для этого процесса.

В Git храним код, миграции, фиксированные зависимости, .env.example,
compose.yaml, инструкции и команду demo_data. Не храним .env, .venv, пароли,
токены, локальные базы, загруженные чеки и реальные персональные данные.
У каждого своя локальная БД; переносим её структуру миграциями, демоданные — командой.

## Запуск и проверка

Команд запуска приложения пока нет: исходный каркас ещё не создан.
Задача BASE-01 должна дополнить этот раздел точной проверенной инструкцией:
версии инструментов → окружение Python → зависимости → настройки → PostgreSQL
→ миграции → demo_data → пользователь мастера → запуск → адрес в браузере.

Нельзя считать BASE-01 готовой, пока по этой инструкции проект не запустили
все трое. Не подменять проверку предположением «у меня работает».

В BASE-01 также подготовить GitHub Actions с PostgreSQL. Для каждого PR:
миграции, Django check, makemigrations --check --dry-run и тесты.

Критические сценарии тестирования:
- две одновременные записи на последнее место;
- запрет просмотра чужой семьи и чужого чека;
- повторное подтверждение платежа;
- повторная отметка посещения и её исправление;
- отзыв ссылки и закрытие существующей сессии.

Задача готова, когда её сценарий работает на реальных моделях, проверки проходят,
изменения объединены и ограничения описаны. Макет с фиксированными числами
может помочь с интерфейсом, но не считается работающим учётом.

## Использование GPT в команде

Каждому помощнику передаём этот README, архитектуру, актуальные модели и одну
задачу из Issue. Указываем критерий готовности. Изменение общих моделей сначала
согласуем; не просим троих помощников независимо создать весь проект.
Перед объединением человек проверяет результат и может объяснить, как работает
его часть. Ошибки передаём с полным текстом и шагами воспроизведения без секретов.

## Следующее действие инициатора

Взять BASE-01: подготовить общий запускаемый каркас и выложить его через PR.
